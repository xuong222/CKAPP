1. 项目目标
-------------------------------------------------------------------------------

1.1 核心目标

在 D:\CH32\SHANGWEJI 中开发一款面向当前 CH32 多传感器固件的 Windows 桌面上位机。
应用通过串口使用 Modbus-RTU 协议与设备通信，提供以下能力：

1. 显示温度、烟雾、PM2.5、CO、CO2、SO2 六项参数数值。
2. 显示综合报警状态，并明确指出发生报警的具体传感器。
3. 读取和写入 40001～40036 寄存器范围内允许操作的参数。
4. 配置串口、波特率、数据位、校验位、停止位、从站地址和响应超时。
5. 提供 Codex 对话框风格的数据收发区，显示完整 TX/RX 原始帧。
6. 支持手动发送十六进制指令、自动追加 CRC、保存常用指令及一键发送。
7. 支持由用户手动开启和停止的定时发送；连接后默认不自动轮询。
8. 提供清晰的异常提示、通信统计、日志筛选、清空和 UTF-8 导出。
9. 发布为 Windows x64 自包含单文件 EXE，可直接双击运行。

1.2 成功标准

1. 无设备时，应用可正常启动、浏览界面、编辑配置，不崩溃。
2. 连接串口后，应用停留在“等待手动指令”状态，不自动发送任何数据。
3. 用户手动发送合法读指令后，原始收发区显示 TX/RX，相关数据卡片正确更新。
4. 用户手动开启定时发送后，应用按指定间隔串行发送当前指令；停止后不再发送。
5. CRC 错误、超时、串口拔出、Modbus 异常响应等情况均有可理解的中文提示。
6. 每一项可写参数均经过客户端范围校验；禁止对只读寄存器执行参数页写入。
7. 中文界面、中文路径、中文日志、中文配置内容均无乱码。
8. 自动化测试、Debug 构建、Release 构建和 win-x64 单文件发布均成功。
9. 最终 EXE 在未安装 .NET 运行时的 Windows x64 环境中可启动。

1.3 非目标（本期不实现）

1. 不修改 D:\CH32\MQTT_UART 中的固件代码。
2. 不实现 Modbus TCP、MQTT、云平台、数据库、用户登录和远程升级。
3. 不添加传感器趋势曲线；该功能已由用户明确取消。
4. 不在连接后默认自动读取；所有自动发送功能必须由用户手动开启。
5. 不实现固件未定义的写操作，不绕过设备寄存器范围限制。
6. 不将“接近阈值”伪装为设备报警；正式报警状态以 40010 位定义为准。

2.2 已识别差异及决策

1. 旧点表写明设备支持 0x03、0x06；当前固件还实现了 0x10。
   决策：上位机支持 0x03、0x06、0x10，以当前固件为准。
2. 旧规约中的未知地址查询示例使用起始地址 0x0100；当前固件仅接受
   [FE][03][00][00][00][01][CRC]。
   决策：内置“查询未知地址”严格使用当前固件定义的 0x0000 起始地址。
3. 点表对报警回差范围的文字与负默认值存在冲突；当前固件明确规定回差不得为正。
   决策：客户端校验以固件 AppAlarm_IsWritableValueValid() 为准，回差只允许 <= 0。
4. 点表写过地址可能断电重启生效；当前固件实现为应答发送完成后切换。
   决策：上位机等待旧参数下的写应答完成，再更新本地地址或波特率。

3. 协议设计
-------------------------------------------------------------------------------

3.1 串口默认值

port = 用户选择
baud_rate = 9600
data_bits = 8
parity = None
stop_bits = One
handshake = None
slave_address = 1
response_timeout_ms = 1000
write_timeout_ms = 1000
periodic_interval_ms = 1000
automatic_send_on_connect = false

串口界面允许用户调整端口、波特率、数据位、校验位、停止位和超时；针对本设备明确提示
推荐值为 9600-8-N-1。波特率下拉至少包含 2400、4800、9600、19200、38400、57600。

3.2 Modbus-RTU 编码规则

1. CRC16 初值 0xFFFF，多项式 0xA001，帧内低字节在前、高字节在后。
2. 寄存器数据按 Modbus 大端顺序传输：高字节在前、低字节在后。
3. 线上的每个寄存器始终是 16 位原始比特；禁止使用“除位掩码外统一按 int16”之类的全局解释规则。
   地址、枚举代码、布尔状态和位掩码按 UInt16 语义解释；测量值、阈值、回差和补偿是否有符号、
   缩放比例、显示精度与合法范围必须逐项取自第 4 节的寄存器定义。
4. 文档编号 40001 对应协议地址 0x0000；协议地址 = 文档编号 - 40001。
5. 支持功能码：
   - 0x03：读保持寄存器。
   - 0x06：写单个保持寄存器。
   - 0x10：写多个保持寄存器。
6. 支持设备私有未知地址查询：FE 03 00 00 00 01 + CRC。
7. 识别标准异常帧：功能码最高位置 1，异常码显示为中文含义。
8. 0xFE 查询是地址匹配的明确例外：请求地址为 0xFE，但设备使用真实从站地址应答。
   只有当响应地址位于 1～64、功能码为 0x03、返回一个寄存器且寄存器值与响应地址一致时，
   才判定发现地址成功；成功后将发现的真实地址填入连接设置，但不自动发送后续请求。

3.3 请求生命周期

状态序列：
Disconnected -> ConnectedIdle -> Sending -> WaitingResponse -> Completed/Failed
Failed(Timeout) -> Resynchronizing -> ConnectedIdle（获得完整静默窗口）/Disconnected（重同步超限）

规则：
1. 连接成功后进入 ConnectedIdle，不创建自动轮询任务。
2. 手动发送、常用指令和定时发送均提交到同一个事务协调器。
3. 同一时刻最多存在一个正在等待响应的 Modbus 事务。
4. 每个软件事务分配单调递增的 TransactionId；请求、日志、超时、取消、UI 状态和响应候选均记录该编号。
   TransactionId 仅用于软件内部关联，不假装它存在于 Modbus-RTU 线上。
5. 根据请求功能码、从站地址和数量推导预期响应长度；收到完整帧后立即校验。
   普通请求要求响应地址与请求地址相同；0xFE 查询按 3.2 第 8 条执行专用匹配。
6. 每个响应候选同时记录 PortGeneration、ReceiveSequence 和单调时钟到达时间；只有当前端口代次、
   当前事务发送之后、事务截止时间之前到达并通过签名校验的候选才可进入成功路径。
7. 超时后事务进入 Resynchronizing，停止定时发送且不得自动重试；事务协调器执行第 3.5 节的迟到响应隔离。
8. 协调器不维护请求等待队列。存在活动事务时，新的手动指令、常用指令、参数写入、专用配置事务和
   定时请求均立即返回 Busy；相同请求也不合并、不排队，避免断线期间积累过期指令。
9. 定时发送使用纯 fixed-delay：只有本次事务完成后才开始等待一个完整设定间隔，间隔结束后发起下一次；
   事务执行期间不存在周期 tick、待合并触发或补发队列，因此任何时刻最多只有一个定时发送流程。
10. 停止定时发送时递增 ScheduleGeneration 并取消令牌；尝试占用协调器前和真正写串口前都必须复核代次，
    从而覆盖“下一次任务恰好准备提交”的竞态。已开始的单次事务允许完成，但不得再安排下一次。
11. 断开串口时递增 PortGeneration，取消等待中的事务与定时计划，并释放串口句柄。
12. 每个 TransactionRequest 明确携带 TransactionMode.Standard 或 TransactionMode.RawDebug：
    - Standard 只能由通过结构、CRC 和请求签名匹配的正常/异常 Modbus 帧完成。
    - RawDebug 不要求请求签名；若响应结构可识别则在结构完整时完成，否则在字节间静默、总响应超时或
      原始捕获上限任一结束条件到达时完成为 RawCaptured。RawCaptured 保留全部原始字节和 CRC/解析状态，
      但绝不更新寄存器快照；完全未收到任何字节才以 TimedOut 完成。

3.3.1 原子完成门

1. 每个事务内部保存 int completionState，初值为 TransactionCompletionState.Pending；枚举至少包含
   Pending、Succeeded、RawCaptured、ModbusException、TimedOut、Cancelled、WriteFailed、Disconnected、ReceiveOverflow、ApplicationStopping。
2. 正常响应、Modbus 异常响应、响应超时、用户取消、串口写失败、串口断开、接收缓存溢出和应用退出全部调用同一个
   TryComplete(TransactionCompletionState newState, TransactionOutcome outcome) 入口。
3. TryComplete 使用以下等价原子门；completionState 必须是 int，避免对枚举误用不适用的重载：
   Interlocked.CompareExchange(ref completionState, (int)newState, (int)TransactionCompletionState.Pending)。
4. 只有观察到旧值为 Pending 的第一个事件是胜者。胜者才可完成使用
   TaskCreationOptions.RunContinuationsAsynchronously 创建的 TaskCompletionSource<TransactionOutcome>，
   并发布一次最终事务结果和一次 UI 状态更新。
5. 竞争失败的事件只记录 TransactionId、候选终态、已胜出终态和到达时间；不得再次完成任务、更新该事务的
   数据卡/错误提示、释放活动事务门或执行事务级清理。若失败方来自真实串口断开或应用退出，连接所有者仍须
   以独立且幂等的连接生命周期入口更新全局连接状态和释放物理端口，但不得反向覆盖已胜出的事务结果。
6. 接收、超时、断开等回调不得直接释放事务互斥门。事务所有者在等待唯一完成结果后，于 finally 中恰好
   释放一次活动事务门；串口生命周期资源由连接所有者恰好清理一次，避免重复释放和关闭竞态。

3.3.2 请求背压与 UI 忙状态

1. 协调器使用原子活动标志实现 TryBeginTransaction；只允许 Idle -> Busy 的一次成功转换，不创建
   ConcurrentQueue、Channel 或其他请求积压容器。
2. Busy 期间的所有新请求立即返回 TransactionRejected.Busy，且不得分配新的 TransactionId、写串口或
   改变当前事务。UI 提示：“当前已有请求等待处理，请完成或取消后再试。”
3. 发送按钮、常用指令按钮、参数下发按钮和特殊配置按钮统一绑定 IsTransactionBusy；Busy 时命令
   CanExecute=false 并显示进行中状态。即使快速双击在 UI 状态刷新前穿透，协调器原子门仍必须拒绝第二次。
4. 定时发送到期时若协调器 Busy，不排队、不追赶；记录一次 Busy 诊断后等待一个完整定时间隔再尝试。
5. 事务完成或取消后，先完成原子终态和资源清理，再把 IsTransactionBusy 复位并通知命令重新计算 CanExecute。

3.4 接收组帧、缓存与多帧拆分

常量与默认值：
- MODBUS_RTU_MAX_FRAME_BYTES = 256（官方 RTU ADU 最大长度）。
- RECEIVE_RING_BUFFER_BYTES = 4096（后台接收环形缓存上限）。
- RAW_CAPTURE_MAX_BYTES = 4096（一次原始调试捕获上限，可容纳粘连的多个标准帧）。
- RESPONSE_TIMEOUT_MS = 1000（可配置 50..5000 ms）。
- RAW_INTER_BYTE_TIMEOUT_MS = max(ceil(t3.5), 10 ms)，可配置 2..1000 ms。
- LATE_RESPONSE_GUARD_MS = max(RESPONSE_TIMEOUT_MS, 100 ms)。
- RESYNCHRONIZATION_MAX_MS = 2 * LATE_RESPONSE_GUARD_MS（随响应超时联动，范围 200..10000 ms）。

字符时间计算：
character_bits = 1 个起始位 + data_bits + (parity=None ? 0 : 1) + stop_bits
character_time = character_bits / baud_rate
当波特率 <=19200 时，t1.5=1.5*character_time，t3.5=3.5*character_time；
当波特率 >19200 时，协议参考值为 t1.5=750us、t3.5=1.75ms。
标准事务以结构长度为主，不依赖 Windows 亚毫秒定时器决定成功；原始调试模式使用较保守的
RAW_INTER_BYTE_TIMEOUT_MS 作为捕获结束条件。

标准事务模式：
1. 0x03 正常响应：读到 byte-count 后，期望总长度 = 5 + byte-count；并验证 byte-count=请求数量*2。
2. 0x06 正常响应：期望总长度固定 8，且回显地址和值必须与请求一致。
3. 0x10 正常响应：期望总长度固定 8，且回显起始地址和数量必须与请求一致。
4. 异常响应：功能码最高位为 1 时，期望总长度固定 5。
5. 任一计算长度不得超过 256；超过时立即判定协议错误，不继续扩容。

原始调试模式：
1. 若功能码结构可识别，优先使用上述结构长度拆帧。
2. 无法推导结构长度时，满足任一条件即结束当前捕获：连续字节间静默达到
   RAW_INTER_BYTE_TIMEOUT_MS、总响应超时、RAW_CAPTURE_MAX_BYTES 上限。
3. 对未知结构可在 4..256 字节候选范围内扫描最早的 CRC 有效边界；存在明确边界时拆出一帧。
4. 静默结束仍无 CRC 有效边界时，将整段数据作为“未解析原始捕获”记录，不伪装成合法 Modbus 帧。

一次底层读取包含多帧时的策略：
1. 从缓存头部循环解析，先按异常帧/已知功能码结构确定长度，再做 CRC。
2. 每拆出一帧即分配独立 ReceiveSequence；剩余字节继续解析，而不是与首帧合并。
3. 当前标准事务只允许第一条匹配候选完成事务；同批次后续帧标记为 Unsolicited，
   只能写日志，不得预先满足尚未发送的未来事务。
4. 一帧被拆成多个底层读取事件时继续累计，直到结构完整、静默、超时或溢出。

缓存溢出处理：
1. 接收缓存或原始捕获达到上限时，当前事务以 ReceiveOverflow 失败。
2. 记录已接收字节数和截断的十六进制摘要；不得把部分帧交给寄存器解析器。
3. 丢弃后续字节直到连续静默达到 RAW_INTER_BYTE_TIMEOUT_MS，再复位组帧器。
4. 溢出后进入 Resynchronizing；未完成重同步前不发送新请求。

3.5 超时、迟到响应与重同步

1. 仅在发送前清空驱动缓存不构成迟到响应解决方案；迟到帧可能在清空后才到达。
2. 请求超时后关闭当前 TransactionId，并进入 Resynchronizing；所有隔离期字节标记为
   LateOrUnsolicited，绝不能完成后续事务。
3. 隔离静默窗口 LateResponseGuardMs = max(ResponseTimeoutMs, 100 ms)。收到任何字节即重新计时，
   只有连续静默满足该窗口后才完成重同步；总重同步时间上限为 2 * LateResponseGuardMs。
4. 重同步达到 2 * LateResponseGuardMs 仍未获得完整静默窗口时，主动断开串口并要求用户重新连接，
   不继续猜测帧归属。
5. 超时事务的请求签名（地址、功能码、起始地址、数量、写入值）保留到重同步完成；
   定时发送不会自动发出相同请求。用户重试前 UI 显示“上一响应可能迟到”的明确提示。
6. Modbus-RTU 没有线上 Transaction ID。若两个完全相同的请求之间存在任意长设备延迟，
   软件无法数学上证明响应属于哪一次请求；设计通过串行事务、静默隔离、禁止自动重试、
   端口代次和内部 TransactionId 降低风险，并必须在日志中保留这种残余歧义，而不是声称完全消除。

3.6 指令输入规则

1. 输入框接受大小写十六进制字符以及空格、Tab、换行、短横线分隔符。
2. 清理分隔符后必须为偶数个十六进制字符，否则禁止发送并显示原因。
3. “自动 CRC”开启时：
   - 用户输入请求主体，上位机计算并追加 CRC。
   - 若用户输入看似已包含正确 CRC，界面提示并避免重复追加。
4. “自动 CRC”关闭时：按用户输入原样发送，但仍在日志中注明是否通过 CRC 检查。
5. 定时发送只能在串口已连接、输入合法、间隔合法时启动。
6. 定时间隔使用正整数毫秒；初始建议范围 100～3,600,000 ms。
7. 单次原始发送长度上限为 256 字节；超过时禁止发送并解释 Modbus-RTU ADU 上限。

3.7 响应更新规则

1. 数据卡片初始显示“--”。
2. 仅当响应完成 CRC、地址、功能码、长度和字节数校验后，才更新寄存器缓存。
3. 读 40003～40008 的响应更新对应数据卡片。
4. 读 40009 更新综合报警继电器状态。
5. 读 40010 更新六项报警位，并在右侧报警栏列出具体报警项。
6. 读 40023 更新六项报警使能状态。
7. 部分区间读取只更新响应实际覆盖的寄存器，不清空其他已有值。
8. 错误响应不得覆盖最后一次有效数值；卡片显示最后更新时间并标记通信错误。
9. 0xFE 查询成功时仅更新“已发现从站地址”和 40001 缓存；不得把 0xFE 当作真实设备地址。

3.8 地址、波特率与恢复出厂专用流程

1. 三类操作获取独占事务锁并自动关闭定时发送，不与普通 0x10 批量参数写入混合。
2. 修改地址：在旧地址下发送 0x06 并验证完整回显；成功后才更新本地从站地址。
3. 修改波特率：在旧波特率下发送 0x06 并验证完整回显；成功后关闭端口并用新波特率重新打开。
4. 恢复出厂：二次确认后在旧配置下写 40036=1；回显成功后切换到地址 1、9600-8-N-1。
5. 任一专用操作响应丢失时，设备可能已经切换，状态必须标记为 ConfigurationUncertain；
   停止全部自动任务，不假定成功或失败，并向用户提供“尝试旧配置”“尝试新配置/默认配置”步骤。
6. 地址变更不确定时可提供 0xFE 查询，但界面必须醒目提示：
   “未知地址查询仅适用于总线上只有一个设备的情况；多设备同时应答会产生总线冲突。”
7. 原始调试模式允许专家自行发送涉及这些寄存器的帧，但不触发自动切换；日志显示风险提示。
8. 无论专用操作成功、失败、进入 ConfigurationUncertain 或重新打开串口，定时发送都保持关闭；
   只有用户再次手动点击“启动定时发送”后才能恢复。

6.4 关键组件

1. ModbusCrc16：CRC 计算与验证。
2. ModbusRequestFactory：构建 0x03/0x06/0x10/0xFE 请求。
3. ModbusResponseParser：解析正常响应和异常响应，返回结构化结果。
4. DeviceRegisterMap：逐项定义 36 个寄存器的 RawEncoding、语义、权限、原始范围、缩放、精度和单位。
5. DeviceSnapshot：保存最后一次有效寄存器缓存和更新时间。
6. ISerialTransport：定义打开、关闭、写入、后台接收数据块、连接状态和 PortGeneration；
   不暴露 System.IO.Ports.SerialPort，供协调器和测试注入使用。
7. SerialPortTransport：ISerialTransport 的生产实现。接收路径只允许一个
   SerialPort.BaseStream.ReadAsync(Memory<byte>, CancellationToken) 后台循环，使用固定大小缓冲块输出数据和
   单调到达时间；禁止订阅 SerialPort.DataReceived，禁止轮询 BytesToRead，禁止再调用 SerialPort.Read/ReadByte。
   打开成功后只启动一个读取循环；关闭时先原子标记 Closing 并递增 PortGeneration，再取消读取令牌，
   随后 Close/Dispose SerialPort 以解除可能仍挂起的 ReadAsync，最后等待读取循环退出。上一循环未退出前不得重开。
   关闭过程中预期的 OperationCanceledException、ObjectDisposedException 和 IOException 只记诊断；
   非关闭过程的读取异常必须报告断线。读取循环逻辑应可用受控 Stream 测试，且不得逐字节发布 UI 事件。
8. RtuReceiveFramer：实现结构长度、静默、CRC 边界、多帧拆分、缓存上限和溢出恢复。
9. ModbusTransactionCoordinator：只依赖 ISerialTransport 和 TimeProvider；分配 TransactionId，
   确保请求串行化，管理签名匹配、总超时、取消、迟到响应隔离和特殊配置事务。
10. PeriodicSendService：依赖 TimeProvider，仅在用户手动开启后以纯 fixed-delay 调度；
    通过取消令牌和代次检查保证停止后不积压任务。
11. FakeSerialTransport：测试专用可编程传输，可精确控制写入、接收块和断开。
12. SimulatedModbusDevice：测试专用模拟设备，解析请求并可脚本化产生正常响应、延迟响应、CRC 错误、
    异常响应、分段响应、两帧粘连、无响应和串口断开。
13. ManualTimeProvider：测试专用可控单调时钟，继承 TimeProvider；推进虚拟时间时同步触发到期计时器，
    使超时、静默窗口、迟到隔离和 fixed-delay 测试不依赖真实等待。
14. SettingsStore：保存非敏感 UI/串口偏好到 UTF-8 JSON。
15. CommunicationLogService：维护 5000 条数据日志和 750 条实时视图投影，并导出 UTF-8 文本。
16. MainWindowViewModel：导航、连接状态和跨页面共享状态。

6.5 线程规则

1. 串口读取、超时等待、文件导出不得阻塞 WPF UI 线程。
2. ViewModel 批量更新 ObservableCollection 或绑定属性时切回 Dispatcher；单字节接收不得直接更新 UI。
3. 串口生命周期使用异步锁或 SemaphoreSlim 防止重复打开/关闭。
4. Modbus 事务协调器只依赖 ISerialTransport 和 TimeProvider，保证一次一个请求；
   任何页面不得直接依赖或写 SerialPort。
5. 定时发送使用 CancellationToken；窗口关闭时必须取消并等待后台任务结束。
6. 所有生产超时、静默判断、时间戳和定时调度均注入 TimeProvider；生产环境使用 TimeProvider.System，
   测试使用 ManualTimeProvider。业务代码禁止直接读取 DateTime.Now，也禁止使用不可控的 Task.Delay。
7. 日志导出使用不可变快照在线程池执行；导出失败不得影响串口接收循环。
8. 不使用 Thread.Abort，不使用无限阻塞 Read，不吞掉后台异常。
9. SerialPortTransport 的接收源只能是单一 BaseStream.ReadAsync 循环；DataReceived、BytesToRead 轮询和
   SerialPort.Read 系列 API 在生产接收路径中均禁止使用，避免重复读取与关闭竞态。
10. 所有 ViewModel 和异步命令使用 CommunityToolkit.Mvvm；事务忙状态变化统一触发相关命令的
    NotifyCanExecuteChanged，不在代码隐藏中另建第二套忙状态。

7. 异常处理与用户反馈
-------------------------------------------------------------------------------

异常类型 -> UI 行为：

1. 端口不存在：阻止连接，提示刷新端口列表。
2. 端口被占用/拒绝访问：保持断开状态，显示端口名称和系统错误摘要。
3. 串口意外拔出：取消事务和定时发送，切换为断开状态，保留日志。
4. 请求超时：记录 TX + 超时系统消息，不修改最后有效数据。
5. CRC 错误：记录完整 RX、期望 CRC 与实际 CRC，不更新寄存器。
6. 地址不匹配：记录为不匹配响应，不当作成功。
7. 功能码不匹配：记录期望与实际功能码，不更新寄存器。
8. 异常响应：显示异常码 0x01/0x02/0x03/0x04 及中文含义。
9. 帧长度/字节数错误：保存原始帧并显示解析失败原因。
10. 参数越界：在发送前阻止写入，并定位具体字段。
11. 配置文件损坏：备份或忽略损坏配置，以默认值启动并提示一次。
12. 日志导出失败：不丢失内存日志，显示目标路径和错误摘要。
13. 接收缓存溢出：当前事务失败，显示缓存上限和已收字节数，完成静默重同步前禁止发送。
14. 迟到/未请求响应：保留原始帧、旧 TransactionId（若可知）和 ReceiveSequence，
    标记 LateOrUnsolicited，不更新数据卡。
15. 地址/波特率/恢复出厂响应丢失：进入 ConfigurationUncertain，停止定时发送并展示恢复选项。
16. 重同步达到 2 * LateResponseGuardMs 仍未恢复：主动断开并要求重新连接，不继续自动尝试。

错误消息不得只显示“失败”；必须包含操作、对象和可行动的恢复建议。

9.3 Infrastructure 测试矩阵

1. 连接后不自动写出任何字节。

5. 纯固定延迟定时发送在单次响应慢于设定间隔时，不产生并发 tick、跳过计数或追赶补发；
   事务完成后必须再等待一个完整间隔才发送下一次。
6. 手动请求和定时请求同时触发：原子活动门只允许一个胜出，另一方立即 Busy；串口无并发写、无请求队列；
   若定时请求被拒绝，必须等待一个完整间隔后才可再尝试。
7. 串口在等待响应时被拔出：事务取消、锁释放、定时停止、UI 状态断开。
8. 响应恰好在总超时边界前/后到达：只能有一个确定终态，不双重完成。

10. 请求 A 与 B 地址和功能码相同：隔离期和禁止自动重试规则生效，TransactionId 日志清楚。
11. 一个底层接收事件包含两帧：拆成两个 ReceiveSequence，仅当前匹配帧完成事务。
12. 一帧被拆成多个接收事件：累计后成功解析，不按单个块误判短帧。
13. CRC 错误、异常响应、无响应、缓存溢出和持续噪声均进入相应失败/重同步路径。
14. 关闭窗口时仍有事务等待：取消完成、后台循环退出、串口句柄释放，无未观察异常。
15. 地址修改响应成功：验证旧地址回显后更新本地地址。
16. 地址修改响应丢失但设备实际已切换：进入 ConfigurationUncertain，不自动假定旧/新地址。
17. 波特率修改响应成功/丢失、恢复出厂响应成功/丢失分别覆盖专用流程。
18. 地址、波特率或恢复出厂流程成功、失败、状态不确定及重新打开串口后，定时发送均保持关闭；
    只有再次手动启动才恢复。
19. 0xFE 查询仅接受真实地址与寄存器值一致的响应；UI/命令模型包含“仅单设备”警告。
20. FakeSerialTransport 与 SimulatedModbusDevice 分别制造延迟、CRC 错误、异常、分段、粘包、
    无响应和断开；ManualTimeProvider 精确推进边界时间；协调器测试不得实例化真实 SerialPort，

21. 日志数据缓存 5000 条、实时视图 750 条分别裁剪；批量 UI 更新不逐字节调度。

23. 配置缺失、合法、损坏三种加载路径。
24. 正常响应、Modbus 异常、超时、用户取消、串口写失败、串口断开、接收溢出和应用退出均只能经 TryComplete
    进入最终状态；每个事件单独覆盖，并至少覆盖响应/超时、取消/响应、断开/超时三组边界竞态。

public bool TryComplete(TransactionCompletionState newState, TransactionOutcome outcome)
{
